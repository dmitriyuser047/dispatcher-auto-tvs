# Расчётное ядро программы

Ядро выделено локально в ветке `codex/program-core`. Эта доработка не опубликована, версия приложения и канал обновлений не переключены.

`assets/core/dispatcher-core.js` управляет расчётными запросами, снимками, доступом и кешем. `assets/core/application-engine.js` подключает пять рабочих модулей. `assets/js/50-engine-bridge.js` передаёт им текущие данные и контекст сеанса из приложения. Ядро можно запускать в Node.js без Electron и интерфейса.

| Модуль | Назначение |
| --- | --- |
| `fuel` | Реестр ГСМ: поступления, расход, распределение по организациям и маркам, замеры, переносы и диагностические основания. Его используют раздел ГСМ и акты. |
| `fuelRecords` | Остатки по записям журнала выбранной машины. Сохраняет прежний контракт журнального экрана. |
| `writeoff` | Подготовка и проверка месячного акта: строки, основания расхода, источники, полнота доступа и готовность к проведению. |
| `costs` | Расходы и выручка по документам, полнота источников и отдельные оценки по ставкам. |
| `procurement` | План потребности топлива и запчастей с заказами, сроками и резервами. Не создаёт фактический приход. |

Расчёт по выписке и расчёт по журналу остаются разными проекциями. Например, при приходе в журнале 20 л и связанной покупке 25 л реестр использует покупку и сообщает о расхождении; журнальный экран сохраняет свои 20 л. Выделение ядра не исправляет исходные записи и не меняет эти правила автоматически.

## Запуск без приложения

```js
const { create } = require('./assets/core/application-engine.js');
const engine = create({ maxEntries: 16 });
const ledger = engine.query('fuel', snapshot, {
  from: '2026-09-01', to: '2026-09-30'
}, { identity: 'database-and-principal-identity' });
const plan = engine.query('procurement', snapshot, { date: '2026-09-30' });
console.log(engine.stats());
```

В Node API дата закупочного прогноза обязательна: скрытые часы не входят в расчёт. Браузерный адаптер подставляет местную дату до формирования ключа кеша. Контекст `readable` ограничивает разделы; он пересекается с `options.readable`, а не расширяется им. Этот механизм дополняет существующие проверки сервера и интерфейса.

## Сохранность и кеш

- На расчёт поступает отдельный замороженный снимок разрешённых разделов. Записи рабочей базы не замораживаются и не изменяются.
- Результаты отделены и от снимка, и от кеша. Изменение полученного объекта, `Map` или `Set` не затрагивает другие запросы.
- Ключ учитывает содержимое зависимых разделов, параметры, идентичность базы, пользователя и доступ. Изменение поля внутри прежнего массива обнаруживается без обязательной смены ссылки.
- Порядок строк сохраняется: он определяет последний замер одного дня. Порядок ключей объекта не создаёт лишних пересчётов.
- Кеш ограничен числом записей и бюджетом содержимого в символах. Слишком большой запрос считается без кеширования. Статистика не содержит исходных записей.
- Запрос журнальных остатков получает только строки выбранной машины. Сохранение, откат и перестроение индексов очищают кеш; успешное сохранение учитывает окончательные данные сервера.

NaN/Infinity, неподдерживаемые типы JavaScript, циклические структуры и повреждённая форма разделов дают явную ошибку. Неполные документы и неизвестные нормы остаются предметными состояниями соответствующих расчётных модулей. Ядро не содержит операций сохранения, миграций базы, сетевых запросов или обновления программы. Существующие команды сохранения и история изменений остаются в приложении и хранилище.

## Списание и сохранённые акты

Раздел **ГСМ и заправки → Списание** теперь показывает подготовку документа, проверку источников, основания каждой строки и реестр актов. Черновик рассчитывается без записи в базу. Действие **«Проверить и провести»** открывает конкретный состав с суммами, номером, датой и основанием. Проведение регистрирует документ в программе; подписи комиссии в печатной форме заполняются отдельно.

Чистый `assets/core/writeoff-engine.js` предоставляет `prepare`, `post`, `voidDocument` и `validateWriteoffChanges`. Он использует тот же реестр, что экран ГСМ. Проверки повторяются в хранилище под блокировкой базы, поэтому обход формы не позволяет сохранить подменённый акт.

- Акт охватывает календарный месяц, выбранные организации и марки дизельного топлива или бензина. Пересекающиеся действующие акты запрещены, включая пересечение общего акта с отдельной организацией.
- Расход делится на введённый факт, расчёт по норме и расчёт по замеру. Холостой ход включается один раз. Нормативный расход требует явного текстового основания. Неизвестная норма не становится нулём при расчёте экономии.
- Ошибки поступлений, отрицательные остатки, неизвестное основание расхода, повреждённые значения и неполные права чтения блокируют проведение. Текстовое основание не снимает ошибки. Корректный большой замер сам по себе ошибкой не считается.
- SHA-256 отпечаток охватывает зависимости расчёта и историю, необходимую для переноса. Изменение источников после просмотра требует повторной проверки. Ошибки прошлого не воспроизводятся как новая месячная проверка; непроверенный переходящий остаток остаётся предметом контроля.
- Раздел `fuelWriteoffs` сохраняет снимок строк, движений, реквизитов, оснований, источников и событий. Автор и время устанавливаются хранилищем. Проведение не создаёт повторного расхода и не исправляет литры или пробег.
- Изменить или удалить сохранённый акт нельзя. Для подтверждённой корректировки сначала выполняется аннулирование с причиной, затем исправляются источники и проводится новый акт. Аннулированный снимок остаётся в истории. Его копия содержит явную отметку об аннулировании и причину.
- Источники действующего акта защищены от изменений. Следующие месяцы, фотографии, статус машины и несвязанные расходы или закупки остаются доступными. Изменение нормы, начальных литров или реквизитов, вошедших в акт, требует аннулирования соответствующего акта.
- Проведённый акт выгружается из сохранённого снимка, включая названия, показания спидометра и приложения. На листе «Паспорт акта» видны идентификатор, состояние, автор, время и основание. Текущие карточки не переписывают старую выгрузку.
- Проведение требует поддержки раздела актов и подтверждённого ответа хранилища с окончательным документом. Старый сервер с ответом только «успешно» не может подтвердить проведение. При конфликте версии автоматическое объединение актов не выполняется.

Новая секция добавляется пустой при открытии старой базы новой программой. Эта разработка и проверки используют временные базы и сохранённую копию для чтения. Рабочая база, установленная программа, инсталляторы и канал обновлений не заменяются.

## Проверки

```powershell
npm run test:engine
npm run engine:demo
npm test
npm run test:ui
npm run test:electron
```

Демонстрация использует только встроенные синтетические данные, ничего не читает из рабочих баз и ничего не записывает. Время выполнения в её выводе — локальное измерение конкретного запуска, а не обещание ускорения любых данных.
