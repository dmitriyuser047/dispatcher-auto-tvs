# Общее ядро программы

Ядро выделено локально в ветке `codex/program-core`. Эта доработка не опубликована, версия приложения и канал обновлений не переключены.

Общее платформенное ядро обслуживает **все сохранения**, а расчётные движки подключаются к нему как предметные модули. Это относится к транспорту, ДЭС, диспетчерской, ТО и ремонтам, складу, закупкам, финансам, реестрам, документам, ГСМ и обмену.

## Платформенная основа

| Компонент | Ответственность |
| --- | --- |
| `assets/core/platform-schema.js` | Единый каталог 10 модулей, 41 раздела и 133 связей. Его используют хранилище, синхронизация и диагностика. |
| `assets/core/platform-integrity.js` | Проверки идентификаторов, дат, чисел, ссылок, прав и завершённых состояний. Удаление объекта не может оставлять новые оборванные связи. |
| `assets/core/platform-policies.js` | Общие предметные правила: занятость техники и сотрудников, подтверждение заданий, приёмка ремонтов, остатки склада. |
| `assets/core/platform-kernel.js` | Подготовка неизменяемых операций, очередь команд, проверка сеанса и прав, подтверждение результата, защита от повторов и события после успешного сохранения. |
| `assets/js/51-platform-bridge.js` | Единая точка входа всех экранов через `saveData`. Передаёт текущую базу, права и версии; безопасно обрабатывает отказ и смену базы. |
| `electron/platform-service.cjs` | Доверенные проверки и история всех нативных и HTTP-записей под блокировкой физической базы. Автор и время берутся на стороне хранилища. |

```mermaid
flowchart LR
  UI[Все формы и импорты] --> Kernel[Общее ядро операций]
  Kernel --> Rules[Права, связи и предметные правила]
  Rules --> Adapter[Нативный или сетевой адаптер]
  Adapter --> Service[Повторная проверка в хранилище]
  Service --> Commit[Атомарная запись данных и истории]
  Commit --> Ack[Подтверждение операции]
  Ack --> Events[Событие завершения и обновление расчётов]
```

Операция содержит устойчивый ID, снимок изменений, версии разделов и перечень изменённых строк и полей. При ошибке проверки запись не начинается. Несколько разделов сохраняются атомарно существующим журналом транзакций. Ответ предыдущей базы не может заменить данные нового профиля или его версии синхронизации.

При поддержке протокола операций сервер сохраняет подтверждение в служебном индексе той же транзакцией, что и изменения. `auditLog` содержит горячую часть событий; остальная история хранится в неизменяемых сегментах. Повтор того же ID, состава, автора и базы возвращает результат без второй записи. Использование ID для другого запроса запрещено. Это работает и после перезапуска хранилища. Клиентская история и указанный в ней автор не считаются доверенными.

Протокол объявляется в снимке базы: `platform: { apiVersion: 1, operations: 1 }`. Сервер подтверждает конкретный ID операции; чтение и запись требуют отдельного согласования совместимости. Неподходящий писатель получает режим просмотра только при подтверждённой совместимости читателя. Подтверждение актов сохраняет свои дополнительные ограничения. Новое принятое намерение сохраняет квитанцию и служебное событие, даже если учётные строки не изменились. Подтверждённый повтор возвращает прежний результат без повторной записи.

Существующие некорректные данные можно изучать и постепенно исправлять: неизменённые старые замечания не блокируют несвязанные правки. Новые ошибки, ухудшение складского дефицита, повреждение ссылок и прямое изменение завершённых состояний отклоняются. Одновременное переназначение или удаление связанных записей проверяется по итоговому состоянию всей операции. Архив сохраняет связи.

История и подтверждения в памяти ограничены числом записей и бюджетом содержимого; большие ответы не остаются в кеше операций. Диагностика и события сеанса не содержат снимков документов, финансовых сумм или реквизитов пользователя. При смене профиля история сеанса отделяется от новой базы.

Экран **«Состояние программы»** доступен в нижней части общей навигации. Он показывает модули, замечания по данным, состояние подключения и последние операции сеанса. Из замечания можно открыть соответствующий раздел. Выгрузка диагностики не содержит полных массивов рабочей базы; открытие экрана и проверка ничего не исправляют автоматически.

## Расчётные сервисы

`assets/core/dispatcher-core.js` управляет расчётными запросами, снимками, доступом и кешем. `assets/core/application-engine.js` подключает пять рабочих модулей. `assets/js/50-engine-bridge.js` передаёт им текущие данные и контекст сеанса из приложения. Ядро можно запускать в Node.js без Electron и интерфейса.

| Модуль | Назначение |
| --- | --- |
| `fuel` | Реестр ГСМ: поступления, расход, распределение по организациям и маркам, замеры, переносы и диагностические основания. Его используют раздел ГСМ и акты. |
| `fuelRecords` | Остатки по записям журнала выбранной машины. Сохраняет прежний контракт журнального экрана. |
| `writeoff` | Подготовка и проверка месячного акта: строки, основания расхода, источники, полнота доступа и готовность к проведению. |
| `costs` | Расходы и выручка по документам, полнота источников и отдельные оценки по ставкам. |
| `procurement` | План потребности топлива и запчастей с заказами, сроками и резервами. Не создаёт фактический приход. |

Расчёт по выписке и расчёт по журналу остаются разными проекциями. Например, при приходе в журнале 20 л и связанной покупке 25 л реестр использует покупку и сообщает о расхождении; журнальный экран сохраняет свои 20 л. Выделение ядра не исправляет исходные записи и не меняет эти правила автоматически.

## Запуск без приложения

```js
const { create } = require('./assets/core/application-engine.js');
const engine = create({ maxEntries: 16 });
const ledger = engine.query('fuel', snapshot, {
  from: '2026-09-01', to: '2026-09-30'
}, { identity: 'database-and-principal-identity' });
const plan = engine.query('procurement', snapshot, { date: '2026-09-30' });
console.log(engine.stats());
```

В Node API дата закупочного прогноза обязательна: скрытые часы не входят в расчёт. Браузерный адаптер подставляет учётную дату базы до формирования ключа кеша. Контекст `readable` ограничивает разделы; он пересекается с `options.readable`, а не расширяется им. Этот механизм дополняет существующие проверки сервера и интерфейса.

## Сохранность и кеш

- На расчёт поступает отдельный замороженный снимок разрешённых разделов. Записи рабочей базы не замораживаются и не изменяются.
- Результаты отделены и от снимка, и от кеша. Изменение полученного объекта, `Map` или `Set` не затрагивает другие запросы.
- Ключ учитывает содержимое зависимых разделов, параметры, идентичность базы, пользователя и доступ. Изменение поля внутри прежнего массива обнаруживается без обязательной смены ссылки.
- Порядок строк сохраняется: он определяет последний замер одного дня. Порядок ключей объекта не создаёт лишних пересчётов.
- Кеш ограничен числом записей и бюджетом содержимого в символах. Слишком большой запрос считается без кеширования. Статистика не содержит исходных записей.
- Запрос журнальных остатков получает только строки выбранной машины. Сохранение, откат и перестроение индексов очищают кеш; успешное сохранение учитывает окончательные данные сервера.

NaN/Infinity, неподдерживаемые типы JavaScript, циклические структуры и повреждённая форма разделов дают явную ошибку. Неполные документы и неизвестные нормы остаются предметными состояниями соответствующих расчётных модулей. Чистые расчётные и платформенные компоненты не выполняют файловый или сетевой ввод-вывод: запись выполняется только через адаптеры и хранилище. Выпуск обновлений отделён от ядра.

## Списание и сохранённые акты

Раздел **ГСМ и заправки → Списание** теперь показывает подготовку документа, проверку источников, основания каждой строки и реестр актов. Черновик рассчитывается без записи в базу. Действие **«Проверить и провести»** открывает конкретный состав с суммами, номером, датой и основанием. Проведение регистрирует документ в программе; подписи комиссии в печатной форме заполняются отдельно.

Чистый `assets/core/writeoff-engine.js` предоставляет `prepare`, `post`, `voidDocument` и `validateWriteoffChanges`. Он использует тот же реестр, что экран ГСМ. Проверки повторяются в хранилище под блокировкой базы, поэтому обход формы не позволяет сохранить подменённый акт.

- Акт охватывает календарный месяц, выбранные организации и марки дизельного топлива или бензина. Пересекающиеся действующие акты запрещены, включая пересечение общего акта с отдельной организацией.
- Расход делится на введённый факт, расчёт по норме и расчёт по замеру. Холостой ход включается один раз. Нормативный расход требует явного текстового основания. Неизвестная норма не становится нулём при расчёте экономии.
- Ошибки поступлений, отрицательные остатки, неизвестное основание расхода, повреждённые значения и неполные права чтения блокируют проведение. Текстовое основание не снимает ошибки. Корректный большой замер сам по себе ошибкой не считается.
- SHA-256 отпечаток охватывает зависимости расчёта и историю, необходимую для переноса. Изменение источников после просмотра требует повторной проверки. Ошибки прошлого не воспроизводятся как новая месячная проверка; непроверенный переходящий остаток остаётся предметом контроля.
- Раздел `fuelWriteoffs` сохраняет снимок строк, движений, реквизитов, оснований, источников и событий. Автор и время устанавливаются хранилищем. Проведение не создаёт повторного расхода и не исправляет литры или пробег.
- Изменить или удалить сохранённый акт нельзя. Для подтверждённой корректировки сначала выполняется аннулирование с причиной, затем исправляются источники и проводится новый акт. Аннулированный снимок остаётся в истории. Его копия содержит явную отметку об аннулировании и причину.
- Источники действующего акта защищены от изменений. Следующие месяцы, фотографии, статус машины и несвязанные расходы или закупки остаются доступными. Изменение нормы, начальных литров или реквизитов, вошедших в акт, требует аннулирования соответствующего акта.
- Проведённый акт выгружается из сохранённого снимка, включая названия, показания спидометра и приложения. На листе «Паспорт акта» видны идентификатор, состояние, автор, время и основание. Текущие карточки не переписывают старую выгрузку.
- Проведение требует поддержки раздела актов и подтверждённого ответа хранилища с окончательным документом. Старый сервер с ответом только «успешно» не может подтвердить проведение. При конфликте версии автоматическое объединение актов не выполняется.

Отсутствующий раздел старой схемы отображается пустым только в представлении для чтения. Для записи нужна отдельная обновлённая копия; открытие исходной базы её не мигрирует. Эта разработка и проверки используют искусственные временные базы. Рабочая база, установленная программа, инсталляторы и канал обновлений не заменяются.

## Водители и операторы ДЭС

В меню доступны отдельные разделы **«Водители»** и **«Операторы ДЭС»**. Оба используют существующий справочник `drivers`: поле `personnelRoles` содержит `driver`, `operator` или обе роли. Старые записи без этого поля остаются водителями без миграции при чтении. Учетные записи приложения и роли сотрудников — разные сущности.

`assets/core/personnel-engine.js` проверяет карточки и новые ссылки на сотрудников в назначениях, заявках и сменных формах. Для транспорта выбирается водитель, для генератора — оператор. Проверки повторяются при записи через общие политики хранилища, включая пересечения дат закрепления одной техники. Исторические ссылки сохраняются; текущие и будущие назначения нужно завершить или переназначить до архива сотрудника либо снятия необходимой роли. Будущее назначение можно отменить с причиной, сохранив запись. Изменение доступности разрешено, но оставшиеся назначения показываются для проверки. Добавление документов разрешено и сотрудникам в отпуске или на больничном.

Карточка хранит контакты, организацию, объект, допуски и сроки удостоверений, медосмотра и инструктажа. Документы и файлы используют `assetDocuments`, закрепление с датами — `assetAssignments`; исходные текстовые имена в старых карточках техники не заменяются автоматически. Предупреждения о сроках документов не являются универсальным запретом работы. Перечни сотрудников в рабочих формах зависят от выбранной техники, а из карточки техники можно открыть закреплённого сотрудника.

`PersonnelPlanning` отделяет закрепление техники от фактической работы по дням. Необязательное `drivers.personnelPlanning` хранит явно заданные периоды графика, включительные интервалы отсутствий и датированные допуски с основаниями. Требования `personnelRequirements` в карточке техники и заявке объединяются. Пустой список заявки не отменяет требования техники. До первого периода графика доступность неизвестна; дни недели и начальные даты автоматически не придумываются. Эта модель описывает гражданские дни, а почасовые смены и оплату труда не рассчитывает.

Запись реального отсутствия или срока допуска сохраняется, даже если старое назначение требует замены. Проверка блокирует новое либо изменённое планирование, а прежние конфликты показывает для исправления. Явная замена закрывает выбранное прежнее закрепление накануне нового в одной операции. Принятие фактически выполненной смены с отклонением от датированного плана требует отдельного основания; оно не меняет пробег, часы и топливо. Новая принятая смена сохраняет `personnelSnapshot` с сотрудником, техникой, заявкой, назначением, организацией, объектом и доказательствами проверки. Последующее редактирование справочника этот снимок не переписывает. Старые принятые смены без снимка остаются прежними и не получают выдуманную историческую принадлежность.

`BusinessCalendar` задаёт общую учётную дату интерфейса и сервера. Без явной настройки действует видимый совместимый режим UTC. Администратор выбирает часовой пояс IANA через проверяемую `CalendarAction` с основанием; настройка и история хранятся в `appMeta`. Ревизия календаря входит в зависимости команд. Повтор уже подтверждённой операции распознаётся до проверки новых часов и настроек.

Новые и явно изменённые интервалы получают каноническое `timeContext` при сохранении. Несуществующее или двусмысленное местное время при переводе часов требует явного смещения. Неизменённым старым строкам зона автоматически не присваивается: их можно подтвердить отдельным действием для действующей заявки или ремонтного заказа. Уже подтверждённые интервалы сохраняют исходную трактовку при смене общей зоны. Ввод клиента не определяет доверенные автора и время операции.

## Сохранённые печатные редакции

`DocumentPrint` формирует самостоятельную печатную модель: точную редакцию документа, реквизиты на момент проведения, доказательства происхождения, версию и отпечаток шаблона. Повторное отображение HTML и подготовка таблицы читают только этот снимок. Текущие карточки, часы системы, новые оплаты и возвраты материалов в него не подмешиваются. У принятого ремонта сохраняется состав материалов на момент приёмки; последующий возврат остаётся отдельным фактом. У принятой смены используется сохранённый `personnelSnapshot`.

Новые проведённые документы получают снимок в той же транзакции с учётными данными и квитанцией. Для прежнего документа без печатного снимка можно явно сохранить позднюю редакцию: её предупреждение не выдаёт нынешнее название справочника за историческое. Числовые и строковые ID различаются. Исправленный документ имеет отдельную редакцию; текущие отчёты используют действующий лист цепочки ровно один раз. Прежний корень с суммой 100 и исправление 80 дают текущую сумму 80.

Архив хранится отдельно в `document-archive/`. Защищённая цепочка в базе связывает неизменные снимки и хеши первых сформированных PDF/XLSX. Файлы публикуются с восстановимым протоколом, а не с обещанием общей атомарности файловой системы и SQLite. Повторная выгрузка проверяет хеш и возвращает прежние байты. Утрата подтверждённого файла считается повреждением архива; программа не заменяет его новой печатью. Создание печатной редакции использует `PrintAction` и общую долговременную очередь. Формирование первого файла обновляет только служебные данные архива.

Предпросмотр и повторная выгрузка повторно проверяют доступ ко всему составу снимка. Скрытый источник не раскрывается через список, историю, квитанцию, файл или выгрузку. PDF формируется в отдельном скрытом окне без скриптов, preload, файловых и сетевых ресурсов. HTML экранируется, а текстовые ячейки Excel не превращаются в формулы.

Ручные путевой лист, заявка ГСМ и акт работ имеют пометку черновика. Пустые дата, организация и сумма остаются неизвестными; ноль сохраняется отдельно. Ручная форма не создаёт выдачу, списание, приёмку либо оплату. Выгрузка акта ДЭС по текущим данным также явно обозначена как черновик. Сохранённые акты ГСМ версий 1–4 не пересчитываются.

Полная управляемая резервная копия переносит архив и проверяет его цепочку. После появления архива ежедневная копия включает его файлы; один JSON с учётными строками не заменяет такой пакет. Самостоятельное восстановление создаёт новую внешнюю идентичность; явное продолжение сохраняет UUID и повышает подтверждённое поколение. Происхождение внутри прежнего печатного снимка сохраняется буквально.

## Контролируемый импорт

`ImportEngine` строит единый план для предпросмотра и применения. `ImportAction` проходит общую очередь команд, проверку версий зависимых разделов и правил непосредственно перед записью. Интерфейс не повторяет собственный цикл слияния и не записывает распознанные строки до подтверждения плана. Смена базы, пользователя, прав, календаря или исходных данных требует повторной проверки.

Оригиналы сохраняются в `import-sources/` с SHA256. Серверный разбор и явно подтверждённая человеком расшифровка различаются. PDF без доверенного классификатора требует полного чтения базы: программа не умеет доказывать отсутствие скрытых сведений на непоказанных страницах. Распознанные значения можно проверить и поправить до составления плана; основание и полный исходный материал остаются в защищённом источнике. Подписанный сервером manifest связан с базой и учётной записью. Подложить JSON вместо серверного результата разбора нельзя.

План показывает исходную строку, сопоставление, сохранённое значение, итог и препятствия. Числовой ID `0` отличается от строки `"0"`; отсутствующее значение отличается от нуля. Изменённый внешний ID или возможное совпадение фактов требует решения. Одинаковые суммы разных ручных покупок сами по себе не доказывают дубликат. История старых импортов и прежние ключи сопоставления сохраняются.

ГЛОНАСС записывает наблюдения отдельно от фактического пробега и расхода по норме. Пересекающиеся суточные итоги требуют явного выбора или подтверждённого суммирования. Расход датчика относится только к подтверждённой части пробега; неизвестные показатели не становятся нулями. Старые скалярные показания без подробных рейсов сохраняются в истории и не прибавляются произвольно к новым. Выписка по топливу не создаёт фактический расход; её привязка к получателю проверяется с учётом прежних выдач. Итоги 1С изменяют только показатели сверки поставщика. Реестр остаётся редактируемым черновиком до подтверждения; запись в ремонт и сохранение реестра не обходят этот этап. Итоговый реестр с неизвестными суммами нельзя выгрузить или сохранить с ложным нулевым итогом.

Полная управляемая резервная копия включает достижимые подписанные источники, оригиналы и ключ проверки. Исторический источник можно читать после восстановления при наличии доступной ссылки на него; применить старый план к другому поколению базы нельзя.

## Область доступа

`AccessPolicy` проверяет роль, действие, пары организации и объекта, поля чтения и изменения. Несколько пар объединяются; организация и объект внутри пары проверяются вместе. Разрешение всех значений задаётся явно. Пустая настроенная область закрывает доступ. Общий справочник не становится доступным для изменения только из-за отсутствия организации.

`AccessScope` определяет принадлежность по сохранённым фактам и проверяемым датированным связям. Текущая карточка техники не доказывает организацию старого журнала. Новое проведение фиксирует подтверждённую принадлежность; прежние строки и документы не переписываются. Неизвестное происхождение закрыто для ограниченной области, а не приписывается выбранной организации.

Движения проверяют обе стороны, распределения — источник и всех получателей. Печать, источники импорта, история и квитанции требуют доступа ко всему составу. Названия, размеры и хеши недоступного исходника также скрываются. Поиск, счётчики и страницы рассчитываются после проверки строк и полей. Один контекст использует индексы связей на весь проход.

Полное доступное представление раздела получает подтверждение `scopeViews`, связанное с правами, ревизией и отпечатком строк. Страница поиска не заменяет это подтверждение. При сохранении сервер восстанавливает скрытые строки, их порядок и закрытые поля под одной блокировкой базы. Проверка исходной и новой области не позволяет присвоить скрытую запись заменой ID. Подтверждение входит в долговременный запрос операции; повтор сначала проверяет прежний результат с текущими правами.

Редактор сетевой учётной записи позволяет задать пары областей, действия, поля и отдельное изменение общих справочников. Смена прав аннулирует открытый план и область кеша. Загрузка ограниченного представления не создаёт общую наличную карту и не присваивает ID старым строкам.

Вложения открываются через типизированную исходную запись. Выбор файла выдаёт подписанное сервером подтверждение байтов, записи, её версии и происхождения. Известный хеш сам по себе не даёт доступа. При открытии повторно проверяются нынешняя запись и первоначальная принадлежность файла. Старые неподтверждённые сведения закрыты в ограниченном представлении. Файловые операции остаются на компьютере с основной базой; передача файлов между клиентами не реализована. Полный резервный пакет переносит и проверяет оригиналы и ключ подтверждения.

## Безопасность интерфейса, файлов и печати

Импортируемые названия, организации, категории, номера техники и пути профилей отображаются как текст. Некорректная дата не передаётся в HTML как исходная строка. Зарезервированные имена объектов не становятся свойствами прототипа. Эти проверки не исправляют и не заменяют сохранённые исходные значения.

PDF создаётся общим изолированным сервисом: отдельная непостоянная сессия, запрет JavaScript, preload, разрешений, новых окон, сети и локальных файлов. Политика ресурсов находится перед печатной формой. Сервис ограничивает вход, время и параметры печати, проверяет текущий контекст после ожиданий и уничтожает окно при успехе, ошибке или отзыве доступа.

Файловые операции фиксируют окно и его главный frame, базу, пользователя и права до первого ожидания. Диалоги, распознавание и выдача результата повторно проверяют контекст; запоздалый прогресс после отзыва доступа прекращается. Чтение идёт через ограниченный файловый дескриптор с проверкой типа, размера и идентичности до и после чтения. Ссылки, подмена файла и рост сверх предела приводят к отказу. Выгрузка проверяет назначение и публикует только законченные байты.

Обработка импортных архивов имеет общий бюджет на весь набор: оригиналы, число элементов, размер каждой записи, суммарная распаковка и глубина вложенности. Имена, объявленные размеры и контрольные суммы проверяются до передачи содержимого следующим обработчикам. RAR обрабатывается отдельным ограниченным процессом; ограничения JavaScript и WebAssembly и таймаут не являются обещанием жёсткого предела общей памяти процесса со стороны ОС.

## Версия базы и миграции на копии

Текущая схема базы — 4. Введённый в схеме 3 дескриптор JSON и SQLite задаёт версию схемы, минимальные версии читателя и писателя, обязательные возможности. Неизвестный или ослабленный дескриптор отклоняется. Старые схемы 1, 2 и 3 новая программа читает без изменения исходных файлов, создания идентичности и восстановления журнала. Старую SQLite она открывает через проверенную отдельную временную копию, чтобы не создавать служебные WAL/SHM в исходном каталоге.

Запись требует актуальной схемы; HTTP дополнительно требует явного подтверждения версии писателя. Подтверждённый повтор операции проверяется раньше этого ограничения, новых часов и конфликтов версий, но возвращает результат только по текущим правам. Отказ происходит до резервирования, распознавания, создания оригиналов, ключей, вложений и первого печатного файла. Уже сохранённые доступные печатные байты можно читать без формирования новой редакции.

Обновление формата создаёт отдельный каталог по проверенному отпечатку источника. Журнал фиксирует этапы и принадлежность временной копии; проверяются данные, порядок строк, типизированные ID, версии разделов и управляемые файлы. Непустой WAL и незавершённый rollback-журнал SQLite останавливают чтение старой базы и создание копии до завершения исходной транзакции. Завершённый PERSIST с полным нулевым заголовком читается без восстановления и изменения источника; наблюдение журнала перепроверяется после чтения. Повтор после прерывания продолжает тот же план с закреплённым UUID. Незавершённая попытка сохраняется, новая собирается в отдельном каталоге; допускается не более восьми сохранённых попыток. Повтор не выполняет рекурсивное удаление файлов. Перед подтверждением опубликованной копии повторно проверяются её UUID, поколение и дескриптор. Завершённые отчёты хранятся в `migration-history/` отдельно от учётных записей. Переключение рабочего профиля выполняется отдельно.

Резервный пакет начиная с версии 2 сохраняет проверенные исходный формат, идентичность и историю миграций. Текущая версия 3 дополнительно сохраняет полное замыкание служебной истории и подтверждений операций. Прежний пакет версии 1 читается с явным неизвестным исходным дескриптором. Восстановление создаёт отдельную базу актуального формата; прежние учётные значения, оригиналы и подписанные исторические материалы переносятся буквально. Старый писатель отклоняет новую схему и новый резервный пакет. Уже выпущенный старый SQLite-адаптер при проверке WAL-базы может создать пустые координационные WAL/SHM; это не является изменением учётных строк, и его прежний код новая программа изменить не может.

## Идентичность, перенос и восстановление

`DatabaseLifecycle` — чистый модуль строгого TypeScript. Перенос сохраняет UUID и поколение текущей базы. Самостоятельная копия получает новый закреплённый UUID и поколение 1. Продолжение из резервного пакета требует явного выбора подтверждённого текущего профиля той же базы: пакет поколения 1 и действующая база поколения 5 дают поколение 6. Неизвестная идентичность прежнего пакета не становится основанием продолжения. Более новое известное поколение, противоречивые метаданные и переполнение номера закрывают операцию.

В «Состоянии программы» действие «Копии и перенос базы» показывает режим, источник, назначение и итоговую идентичность до создания. Восстановление резервного пакета использует такой же проверяемый план. Изменение полей отменяет подтверждение. Сохранённый план открывается со своими закреплёнными параметрами; при другом намерении нужен новый план. Ни создание копии, ни восстановление автоматически не переключают профиль и не удаляют исходник.

Main хранит подписанный HMAC план в служебном каталоге своего профиля, отдельно от учётной базы. Renderer передаёт только выбранные параметры, а при применении — непрозрачный ID и отпечаток проверки. Исходный каталог, пользователь, ключ, новый UUID и поколение задаёт доверенный процесс. Проверяются окно и главный frame, контекст, каталог назначения, свежие метаданные поколений и полный отпечаток источника перед публикацией. Журнал v2 закрепляет весь явный план; прежний исполнитель журнала v1 не может принять его за обычную копию. После публикации повтор проверяет реальную целевую идентичность и возвращает прежний результат без новой копии, нового поколения или повторной проверки уже изменённого исходника.

Диагностика профилей запускается явно и читает только перечисленные в настройках каталоги. JSON проверяется по метаданным, SQLite — через поддержанный immutable reader без бизнес-таблиц, создания идентичности и служебных файлов. Занятый или неподтверждённый профиль имеет явное состояние. Показываются совпадающие физические папки, одинаковые идентичности в разных папках и разные поколения. Сканирование дисков и автоматическое исправление идентичности не выполняются.

Старые очереди, квитанции и подписанные источники сохраняют первоначальную принадлежность. Координатор отклоняет запрос чужого токена до постановки в очередь и до транспорта. Новый путь, UUID или поколение не переносят неизвестные операции на другую базу.

## Совместимость клиента и сервера

`PlatformCompatibility` — общий чистый модуль строгого TypeScript. Он согласует конкретную версию протокола, схемы читателя и писателя и обязательные возможности. Подтверждённый совместимый читатель без подходящего писателя получает режим просмотра. Если возможность чтения не подтверждена, интерфейс не получает строки базы. Неизвестный протокол, версия или обязательная возможность не считаются совместимыми по умолчанию.

HTTP выдаёт короткоживущее подписанное разрешение записи. Оно связано с процессом сервера, базой и поколением, действующим пользователем, ролью, ключом, политикой доступа, дескриптором и выбранным профилем совместимости. Main хранит разрешение только в памяти. Renderer, очередь и сохранённый запрос его не получают. Обновление разрешения не меняет намерение операции, digest, исходные версии, область очереди или токен базы. Подтверждённый повтор доступной операции разрешается проверить до требования нового разрешения и до CAS; новое намерение без актуального подтверждения не записывается.

Обычное сохранение всегда передаёт явные исходные версии разделов и токен прочитанной базы. Подстановка текущих версий и переход к полной записи при неподдерживаемом протоколе исключены. Формы показывают режим просмотра до редактирования. Смена профиля, прав, окна, frame или адреса во время ожидания отменяет позднее чтение и отправку. Окно распознанного реестра повторно проверяет владельца и актуальный контекст перед выдачей своих данных. Создание оригинала, вложения и нового печатного файла требует соответствующей возможности перед чтением входа и перед публикацией; доступное сохранённое содержимое читается без разрешения новой записи.

## История и подтверждения операций

Формат базы 4 добавляет обязательную возможность `operation-receipts-v1`. Он создаётся только в новом каталоге или управляемой копии. Старые источники читаются без автоматической миграции; прежний писатель схемы 3 отвергает новый формат.

Горячий раздел `auditLog` содержит не более 5000 событий. Остальная история хранится в неизменяемых сегментах, а компактные подтверждения — в отдельном индексе по исходному operationId. Журнал JSON публикует новые бизнес-разделы и служебный head одной транзакцией; SQLite делает это в одном внешнем COMMIT. Потерянный ответ не теряет квитанцию. Повтор проверяет точный digest, автора, базу и действующие права до нового разрешения записи, CAS и часов.

В «Состоянии программы» история читается по 25 доступных событий, включая архив. Поиск применяется после ограничения строк и полей. Страницы не раскрывают глобальные количества и внутренние номера; продолжение связано с пользователем, правами и первоначальной границей выборки. Сохранённая принадлежность обеих сторон не выводится из сегодняшней карточки. Неподтверждённая старая история доступна глобальному администратору. Объединение справочников отдельно проверяет полную логическую историю и сохраняет архивные ссылки.

Резервный пакет manifest3 включает полное проверенное замыкание индекса и сегментов. Перенос не переписывает происхождение квитанций, подписей или прежних актов. Большая старая история архивируется только при явном создании управляемой копии, с сохранением каждого исходного события.


## Техническая диагностика

Операция сохраняет исходный ID при подготовке, постановке в очередь, передаче, физической записи и получении подтверждения. Диагностический наблюдатель не определяет результат операции. Потерянное или несовпавшее подтверждение остаётся неизвестным; его нельзя заменить техническим сообщением об успехе.

Отдельный каталог профиля хранит до четырёх файлов по 64 КиБ. Разрешены только фиксированные этапы и коды, ограниченные числовые метрики и HMAC-псевдонимы ID. Сырые исключения, бизнес-строки, пути и ключи не записываются. Отметка времени относится к записи события в журнал; длительность обработки измеряется отдельно монотонными часами. Наблюдения могут вытесняться при перегрузке или завершении приложения: это журнал для поиска проблем, а подтверждения операций по-прежнему хранятся атомарно в базе.

Администратор открывает техническую цепочку по ID операции в «Состоянии программы». Кнопка «Пакет для поддержки» создаёт новый ZIP только по явному действию. В него входят технические события и manifest с хешем; база, настройки и диагностический ключ не входят. Каждый пакет получает новые псевдонимы, поэтому пакеты разных компьютеров автоматически не объединяются. Исходный ID позволяет найти операцию локально на каждом компьютере.

Проверка подключения передаёт временную занятость локальной базы и отзыв доступа отдельными фиксированными результатами без данных, идентичности, прав или токена. Дополнительные свойства исключений теряются при переходе через Electron IPC и contextBridge, поэтому интерфейс разбирает результат после проверки текущего сеанса. Краткая локальная блокировка сохраняет уже подтверждённый снимок; отзыв доступа очищает приватный вид. Неизвестный результат, новое подключение без подтверждения и занятость удалённого сервера не разрешают запись. Эти переходы проверены через настоящий IPC для JSON и SQLite, включая блокировку независимым читателем и фактический отказ сервера.


## Проверяемый локальный кандидат

`scripts/local-release-candidate.cjs prepare` создаёт новый каталог `audit/local-candidate-…` с контрольными суммами исполняемых исходников, конфигурации, деклараций зависимостей и lockfile, тестов и включаемых ресурсов. Коммит записывается как происхождение. При сборке отдельно закрепляются фактические байты всех staged-зависимостей и их точные пути в ASAR. Изменение только документации или коммита без изменения проверяемых байтов не делает результаты устаревшими.

В этом каталоге команда `gate <каталог> <unit|ui|native|benchmark>` сама запускает фиксированный полный рецепт. Готовые чужие журналы не принимаются. Для каждого прогона проверяются исходники до и после, код завершения, полнота результата и хеш журнала. Нагрузочный рецепт использует только новые синтетические базы на 1000, 5000 и 10000 записей. Ошибка оставляет результат незавершённым; сборка без всех четырёх успешных проверок запрещена.

`build <каталог>` использует только локальный Electron и `electron-builder --dir --publish never`. Он создаёт отдельный `candidate/win-unpacked`, закрепляет точные файлы stage, ASAR, распакованные ресурсы и исполняемый файл. Готовность `VERIFIED` выдаётся только после `test-candidate <каталог>`: четырнадцать сценариев выполняются в самой программе кандидата, ещё два проверяют PDF и RAR из его ASAR. Все процессы используют скрытые отдельные тестовые профили. Команда `verify <каталог>` повторно проверяет доказательства и файлы кандидата.

Существующий установщик, версия и канал обновлений не изменяются. Этот рецепт не создаёт установщик, не устанавливает программу и ничего не публикует. Рабочая база и рабочий профиль не являются входами испытаний.

Сохранение остаётся синхронной транзакцией основного процесса. В последнем приёмочном нагрузочном прогоне изменение примечания одной записи в разделе из 10000 строк заняло 16,77 секунды в JSON и 15,20 секунды в SQLite; в предыдущем — 21,43 и 16,19 секунды. Фоновые расчёты и страницы запросов работают отдельно; эти измерения не означают мгновенного сохранения произвольной базы.
